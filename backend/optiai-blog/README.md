# Блог OptiAI для Poehali

Эта функция хранит статьи отдельно от таблицы заявок. Публичный POST расположен
на домене сайта по адресу `/api/optiai`; он проксирует запрос в функцию.
Статьи выводятся сервером по `/blog` и `/blog/:slug`, изображения по
`/blog/media/:id`, карта блога по `/blog/sitemap.xml`.

Перед включением:

1. Сохранить копии исходников и базы проекта.
2. Выполнить `schema.sql` в базе проекта. SQL создаёт только две новые таблицы.
   Повторное выполнение добавляет `schema_json` к ранее созданной таблице статей.
3. Создать функцию `optiai-blog` из `index.py` и `requirements.txt`.
4. Убедиться, что Poehali добавил URL функции в `backend/func2url.json`. Если
   это не произошло, задать для серверного сайта секрет
   `OPTIAI_BLOG_FUNCTION_URL` с точным HTTPS URL функции на
   `functions.poehali.dev`.
5. Для функции задать `OPTIAI_CONNECTOR_TOKEN`: уникальная случайная строка не
   короче 32 байт, одна на канал. Указать `OPTIAI_MEDIA_HOSTS=optiai.ru` либо
   точные хосты изображений, используемые OptiAI. Токен не записывать в код.
6. После публикации проверить `/blog`, `/robots.txt`, `/sitemap.xml` и
   `/blog/sitemap.xml`. Затем разместить выданную OptiAI строку в
   `/.well-known/optiai-verify.txt` и пройти проверку подключения без записи.

Функция принимает `capabilities`, `diagnostics`, `dry_run`, `publish`,
`get_article`, `update_article` по протоколу custom connector v1.1. Повторная
публикация того же slug обновляет запись с тем же ID. `dry_run` ничего не пишет.
`capabilities` заявляет `safe_errors_v1`; отказы возвращают только разрешённые
`error_code`, `field`, `reason_code` и случайный UUIDv4 `request_id` без токена,
HTML и произвольного текста ошибки. Проверка подключения отклоняет
`dry_run` со slug `../invalid` как HTTP 400, `validation_failed`, `slug`,
`invalid_slug`, не создавая статью.

Версия клиентского коннектора 2.5.2. При проверке HTML используется HTML5-парсер:
неизвестные теги и атрибуты, дубли атрибутов, обработчики событий, исполняемые
скрипты, внешние `script src`, `javascript:`-ссылки, `meta refresh` и опасные
стили отклоняются. Разрешены только явно перечисленные безопасные теги и
атрибуты. У `<meta>` можно использовать любое корректное текстовое имя
`itemprop` вместе с `content`; порядок атрибутов и вид кавычек не важны.
Встроенный `application/ld+json` проверяется как JSON и выводится в `<head>`
с `id="optiai-seo-schema"` для Article без дублирования. Исходный HTML статьи
хранится отдельно; для публичной страницы меняются только адреса изображений
на локальные и размещение JSON-LD. Новые виды HTML требуют явного пересмотра
списка разрешений и теста финального payload OptiAI.

Для отката удалить из маршрутов только блог и прокси, вернуть прежние Header,
Footer, robots и sitemap. Таблицы блога оставить для сохранности статей и
медиа. Таблица заявок не меняется.
При откате версии 2.5.2 вернуть предыдущие `index.py` и маршруты блога, но
оставить колонку `schema_json`: её удаление может повредить уже опубликованные
статьи. Перед возвратом проверить, что на публичных URL сохраняется Article
JSON-LD и карточка авторства; если нет, приостановить публикацию до ремонта.
